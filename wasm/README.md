# soroauth WebAssembly signing core

## Exported API Rationale & Limitations

- **preimage**: Derives the signing `HashIdPreimage` and its 32-byte SHA-256
  payload locally in the browser, eliminating reliance on a trusted server.
  _Limitation_: Source-account entries have no preimage and throw an error
  rather than returning empty success.
- **payload**: Hashes an already constructed preimage (base64 XDR) to its
  32-byte digest, supporting remote signers without entry reconstruction.
- **writeSignature**: Writes an externally produced signature `ScVal` onto
  target credential nodes, maintaining strict isolation of signing keys.
- **authorizeWithSeed**: Provides a deterministic test and local demo path using
  an in-memory raw ed25519 seed.

## Production Readiness

The WASM build is fully production-ready for deriving preimages and writing
signatures (such as passkey credentials) in browser environments. However,
callers must ensure correct resource fees and execute the two-pass simulation
flow prior to submitting transactions on-chain.

The signing core builds for `js/wasm`, so a browser can derive the bytes it
signs rather than trusting a server to supply the payload. That is what makes
passkey signing viable: the wallet builds the preimage, hashes it, and only then
asks the authenticator to sign.

| Path                   | What it is                                                                                        |
| ---------------------- | ------------------------------------------------------------------------------------------------- |
| `../cmd/soroauthwasm/` | The js/wasm entry point. A thin JavaScript binding over the shared core; it reimplements nothing. |
| `../cmd/soroauthwasi/` | The wasip1 entry point. A JSON-over-stdio binding over the same `internal/wasmcore` package.      |
| `build.sh`             | Builds both targets, copies the matching `wasm_exec.js`, and writes `dist/SHA256SUMS`.            |
| `parity.mjs`           | Replays every golden vector through the js/wasm build and asserts byte-identical output.          |
| `wasi-parity.mjs`      | Replays the same vectors through the wasip1 build under Node's WASI runtime.                      |
| `ts/`                  | The `@soroauth/wasm` TypeScript wrapper package.                                                  |
| `dist/`                | Build output. Not committed; regenerated by `build.sh`.                                           |

## Build and verify

```sh
./wasm/build.sh             # or: make wasm
node wasm/parity.mjs        # or: make wasm-check (js/wasm)
node wasm/wasi-parity.mjs   # or: make wasi-check (wasip1 under Node WASI)
```

`parity.mjs` and `wasi-parity.mjs` compare the preimage, the payload and the
final signed entry against the recorded vectors — the same bytes the native
build and `@stellar/stellar-sdk` already agree on — and exit non-zero on any
mismatch. Source-account entries have no preimage and are skipped loudly, with
the pass-through path verified instead.

`build.sh` writes `dist/SHA256SUMS`, and the release publishes the same digest
as `soroauth-wasm-checksums.txt`. `scripts/reproduce-wasm.sh <tag>` rebuilds the
tagged source twice and fails on any difference; see
[docs/reproducibility.md](../docs/reproducibility.md). Both targets are built
with `-trimpath -buildvcs=false`, so the checkout path and VCS stamp do not
enter the bytes.

## WASI (no JavaScript host)

`soroauth.wasi.wasm` is the same core built for `GOOS=wasip1`. It needs only
stdin and stdout: send one JSON request and read one JSON response, for
`preimage`, `payload`, `writeSignature` or `authorizeWithSeed` (the request
field names match the js/wasm arguments). It has no filesystem access, no
network access and reads no environment variables. Node 22+ runs it with
`node wasm/wasi-parity.mjs`; `wasm/wasi-run.mjs` shows the minimal WASI host.

## Calling it

The module installs `globalThis.soroauth` with four functions, each returning
either `{ ok: true, ... }` or `{ ok: false, error }`:

- `preimage(entryB64, validUntilLedger, networkPassphrase)`
- `payload(preimageXdrB64)`
- `writeSignature(entryB64, validUntilLedger, networkPassphrase, forAddress, signatureScvalB64)`
- `authorizeWithSeed(entryB64, validUntilLedger, networkPassphrase, seedHex, forAddress)`

In practice use the TypeScript wrapper, which gives these real types and turns a
`{ ok: false }` into a thrown `SoroauthError`:

```ts
import { loadSoroauth } from "@soroauth/wasm";
```

## Why the whole package is build-tagged

Every file in `cmd/soroauthwasm` carries `//go:build js && wasm`, so
`go build ./...` and `go vet ./...` skip it on the host (a directory with no
buildable Go files is not an error). CI builds it explicitly in the `wasm` job —
the only place it is compiled, which is why that job exists rather than relying
on `go test`.

The interactive TUI in the root package is excluded from js/wasm builds because
bubbletea does not compile for that target; the CLI, which is never built for
js/wasm, is unaffected.
